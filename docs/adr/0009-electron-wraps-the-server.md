# Electron wraps the server rather than absorbing it

The Desktop App is the same app `docker compose up` runs. Electron's main process starts the built Nitro server (`.output/server/index.mjs`) as a child process on a loopback port and points a window at it; every API route, every Job, the range-request streaming a browser needs to seek within a Backing Track, the AudioWorklet engines, and all sixteen files in `tests/api/` are untouched. A future reader will absolutely ask why a desktop app runs an HTTP server and talks to itself over TCP, and this is the answer.

The real alternative was absorbing it: move `server/lib/` into the main process and replace HTTP with IPC, which is what most Electron apps look like. It was rejected on four counts, none of them aesthetic. It breaks range-request seeking on the Backing Track, because `Range`/`206` is an HTTP contract the `<audio>` element speaks and an IPC channel does not. It breaks audio decoding through `/api/tracks/:id/backing` for the same reason. It breaks every test in `tests/api/`, which drive real route handlers over real HTTP. And it forks the codebase in two: a browser path and a desktop path, diverging from the first bug fixed in only one of them — for a project whose entire self-hosting story is the browser path.

So the shell is thin on purpose, and staying thin is the point (spec user story 8): almost every change to Akapela still belongs in the Nuxt app, and `desktop/` should stay small enough to read in one sitting. `desktop/src/` is roughly a dozen files, and the two things in it that genuinely need an operating system — a native folder picker and opening a link — are the entire preload bridge.

## Consequences

- **Loopback only, and therefore no authentication question.** The server binds `127.0.0.1`. The absent authentication the README warns about is a deliberate LAN trade-off in a container; on a laptop on public wifi it is not, and binding loopback makes the question disappear rather than answering it. Anyone who wants Akapela on their network runs compose, which is unchanged and still first-class.
- **The port is persisted, not allocated per launch.** This is the non-obvious part. `localStorage` is keyed by origin, and `http://127.0.0.1:54321` and `http://127.0.0.1:61234` are different origins. Four per-device settings live in `localStorage` — the output volume (`app/audio/volume.ts`), the theme (`useTheme.ts`), the latency nudge (`useTakeReview.ts`), and the chosen microphone (`useTakeRecorder.ts`) — so a fresh port each launch would silently reset all four every time. One port is chosen from the dynamic range on first run, stored beside the window bounds, and reused; a launch that finds it taken picks another and accepts resetting those four once (`desktop/src/port.ts`).
- **The child is Electron's own binary run as Node.** `ELECTRON_RUN_AS_NODE=1`, so there is no second runtime in the installer. That variable has to reach the server's own subprocesses too: under Electron `process.execPath` is the GUI binary, so spawning it plainly launches a second copy of the app instead of running the separation CLI. `server/lib/tools.ts` sets it on every child, unconditionally, because plain Node ignores it and one code path is better than two.
- **Electron is the supervisor, and that is what makes restore work.** `POST /api/backup/restore` deliberately calls `process.exit(0)` and relies on something outside the process to bring a fresh one back. Compose's `restart: unless-stopped` does that; `pnpm dev` does not, which is what the two-minute timeout message in `app/pages/settings.vue` exists to explain. With Electron restarting the child, restore-and-restart simply works — and works better on the desktop than it does in the dev loop.
- **Quitting is not guarded.** The server is asked to shut down so the Job runner's `close` hook runs, with a hard kill after a few seconds. A Job caught mid-run stays `running` and the Track offers a retry, exactly as it does after a `docker compose down` mid-separation. No "a Job is running, are you sure?" dialog; add one later only if it turns out to bite.
- **The renderer loads over `http://`, never `file://`.** This is load-bearing rather than stylistic: `file://` is not a secure context, which would take `getUserMedia` and the AudioWorklet engines with it. The only pages the shell renders itself are a loading state and an error state, both inline `data:` URLs, so there is never an `index.html` to be tempted by.
- **Native modules need no rebuild, and this is worth recording so nobody spends a day on it.** `better-sqlite3` v13 is node-addon-api and ships `prebuilds/<platform>-<arch>.node` keyed by platform alone; `onnxruntime-node` ships `bin/napi-v6/<platform>/<arch>`. Both are N-API, so both load under Electron unrebuilt. There is no `@electron/rebuild` step.
- **Both paths read the same data directory and the same `akapela.db`**, so a backup archive moves between the Desktop App and a compose instance in either direction, and a Desktop App can be pointed straight at a folder a compose instance built.
- **No e2e harness.** The logic worth testing is pure and lives in the root vitest suite — the port rules, the window bounds, the config store, the packaged layout, the version check — none of which import Electron. What is left is thinner than a Playwright rig would be.
- **Native audio stays out of scope.** No ASIO/WASAPI/CoreAudio path and no second audio engine outside the renderer. Recording latency is already handled by the Review screen's nudge (ADR 0006), and automatic latency calibration is its own roadmap line.
