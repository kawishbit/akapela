# ffmpeg is bundled in the installer; yt-dlp is fetched into the library

Akapela shells out to three external binaries, and the Desktop App treats them asymmetrically. `ffmpeg` and `ffprobe` ship inside the installer and are never expected on the singer's machine. `yt-dlp` does not: it is downloaded on first use into `<dataDir>/cache/bin/`, and an **Update yt-dlp** button in Settings replaces it.

The asymmetry is the surprising part, so it is the part worth recording. ffmpeg is stable and load-bearing — every import normalizes through it and every Mix renders through it — and a missing one is not a degraded app but no app at all. yt-dlp is the opposite: it chases a site that changes without warning, and it breaks every few months by design. That is not a defect in yt-dlp; it is the job.

What makes that intolerable rather than merely annoying is who is holding it. The README's answer to a broken yt-dlp is `git pull && docker compose up -d --build`, and that answer only exists for someone who cloned a repo. Someone who downloaded an installer has nothing to pull, and YouTube import — the app's main way of getting a song in — would simply stop working until the next release. Putting the binary in the library's cache rather than inside the app means the app can replace it, and the breakage that used to need a rebuild becomes one click. It is the one thing the Desktop App can do that the container cannot.

The cache path is not a new idea here: the separation model already lives at `<dataDir>/cache/models/` and is fetched on first separation (ADR 0008). `cache/` is a deliberate namespace — everything under it is re-downloadable, which is what lets a backup exclude it by one rule. yt-dlp joining it means it survives app updates exactly as the model does.

## Consequences

- **The compose path is untouched.** The image still bakes yt-dlp in and still finds it on `PATH`; nothing there downloads or replaces a binary, and the Settings control is absent. The whole difference is whether the desktop shell set `AKAPELA_YTDLP` and `AKAPELA_MANAGE_YTDLP` (`server/lib/tools.ts`).
- **Every external tool sits behind one seam.** `server/lib/tools.ts` reads an environment override per tool and otherwise returns what the code returned before: the bare name off `PATH`, or the separation CLI resolved against `process.cwd()`. Deliberately the dumbest thing that works — no detection, no probing, no registry — because the alternative is two code paths where compose and the desktop drift apart.
- **The bundled binaries are pinned with checksums, not followed.** The Dockerfile fetches `latest`, which is fine for a self-hoster building an image on their own machine and not fine for a binary you sign and hand to other people. `desktop/scripts/binaries.json` names one immutable build per platform with the SHA-256 its archive must have, and `fetch-binaries.ts` fails loudly on a mismatch — and equally loudly on an entry nobody has verified.
- **Any stock static ffmpeg will do, per platform.** This used to say "always BtbN's `gpl` variant", because the Mix render used ffmpeg's `rubberband` filter and BtbN strips librubberband out of every `lgpl*` build. The render now stretches with Rubber Band WebAssembly instead (ADR 0003 and ADR 0004 amendments), so a build only has to carry libmp3lame, the decoders the imports need, and ordinary filters. That change is what let Apple Silicon ship at all. BtbN publishes no macOS builds, and no publisher ships a static arm64 macOS ffmpeg with librubberband. `darwin-arm64` is now martin-riedl.de's pinned 9.0.1 release, checked for arm64-only, for loading nothing outside macOS, and for libmp3lame. Windows and Linux are still BtbN's `gpl` builds.
- **Distributing GPL binaries brings a licence obligation, and it is a small one.** The texts ship in the installer and the app links to them (**Help › Source and Licences**). Nothing more elaborate.
- **A first YouTube import on a new machine pays for a download.** It happens when an import needs it, not at startup, so every import after the first pays nothing. A failed fetch fails the Track with a message and a retry rather than leaving it stuck, in the same voice `ModelDownloadError` uses.
- **The runtime yt-dlp needs came free.** YouTube's player challenges are solved by running JavaScript in an external runtime, and a singer who downloaded an installer has no Node on their `PATH`. Rather than vendoring a fourth binary, the shell hands yt-dlp `--js-runtimes node:<path to Electron>` and lets `ELECTRON_RUN_AS_NODE=1` do the rest — Electron is Node wearing a costume, and it is already in the installer. If that ever stops holding, a standalone Deno or QuickJS is the fallback, at the cost of bytes and no cleverness.
- **The separation CLI ships precompiled.** `separate-cli.ts` is run directly by Node's native type-stripping today, and betting a signed installer on Electron's Node having that enabled is not a bet worth taking. It is three files plus `app/audio/wav.ts`, compiled at pack time.

## Amendment: only ffmpeg ships; ffprobe does not

ffprobe was bundled for one number, the duration of a Backing Track, and on Windows it cost 164 MB, a second full static copy of every codec. Every file the app ever asked the duration of is a WAV it wrote itself: a Backing Track `normalizeToBackingTrack` produced, or a Stem the separation encoded. `wavDurationMs` in `server/lib/audio.ts` now reads the duration from the file's header, as the data chunk's size divided by the byte rate. That is the same arithmetic ffprobe does for PCM, and a test holds the two to the same answer.

- **No installer, and no compose image, carries ffprobe.** `binaries.json` pins the same archives with the same checksums; `fetch-binaries.ts` just takes one member out of them rather than two. Where the archive is per-binary (macOS), only `ffmpeg.zip` is fetched.
- **`AKAPELA_FFPROBE` is gone** from the tool seam, and the AppHost no longer checks for ffprobe on the `PATH`. Only the test suite still runs it, to check what the app wrote. A contributor gets it with the same ffmpeg package.
- **The builds themselves did not change.** BtbN's `lgpl` static builds are only about 10% smaller than `gpl`, and a shared build's libraries weigh about what one static ffmpeg does. Dropping the duplicate binary was the saving; swapping builds would have meant re-verifying every format on every platform for a fraction of it.
